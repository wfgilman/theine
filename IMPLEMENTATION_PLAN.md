Conventions:

- One task = one commit = one build-loop iteration, under an hour.
- Tasks are ordered so that every dependency sits above its dependents. The
  build loop takes the topmost unchecked task.
- Tasks marked **(hot path)** touch `Theine.get/2`, `Theine.put/4`,
  `Theine.ReadBuffer` or `Theine.Entry` and must run `mix bench get` and paste
  the summary table into the commit body (AGENTS.md).
- Tasks marked **(maintenance)** must run `mix bench maintenance`; tasks marked
  **(policy)** must run `mix bench hitrate` (specs/10 §Gates, step 6).
- Stress-tier tests are tagged `:stress` and excluded from `mix test`
  (specs/10 §Tiers).

## Discovered issues


1. **`nebulex_local` availability** (resolved in M5.1). Nebulex 3 splits the local adapter into its own package: `nebulex_local` 3.1.0 pairs with `nebulex` 3.1.0 on Hex (both 2026-10-18), and both are dev-only deps.
2. **Concurrent writes to one key can leave the policy with the wrong id** (found in M1.2, resolved in M1.5). `put/4` allocates the id before the insert, and the write event is sent after it, so two writers racing on one key can produce any interleaving of (insert, send) pairs: the entries table may end with the lower id while the policy applies the higher id's event last, or vice versa. The spec's rules (last `:put` event wins; `on_remove` ignores a stale id) then left a policy row whose id never matched the table; in an unbounded cache `size/1` drifted by one and `delete/2` could not clear the row. Resolved as recommended (specs/05 §Decisions 2026-10-27 M1.5): `on_remove(key, id)` with a non-matching id does one `:ets.member/2` on the entries table and drops the row when the key is absent; when the key is present with a third id, the row stays and that id's `:put` corrects it. Tested in policy_test, maintenance_test and the 200-round race in theine_test. Since M3.2 a lower id's `:put` arriving after a higher id's is applied only while the table holds it, so one direction of the reorder no longer leaves the row on a stale id (specs/05 §Decisions M3.2).
3. **A write that straddles `clear/1` can leave a policy row with no entry** (noted in M1.5, not fixed). A writer that inserted before `:ets.delete_all_objects/1` and whose `:put` event is consumed after `Maintenance.reset/1` re-adds a policy row for a key the table no longer holds. No later event for that key arrives on its own (a `delete/2` of an absent key sends nothing), so in an unbounded cache the row lives until a `put` of the same key or a Maintenance restart rebuild (M2.9). In a bounded cache the eviction re-lookup drops it. The window is a few microseconds per `clear/1` and the cost is one phantom entry in `size/1`; the spec accepts it (specs/01 §Write path `clear/1`). If it matters later, `reset/1` could record the `ids` high-water mark and `on_write` ignore `:put` events with a lower id until the table confirms the key.

4. **The `ets` p99 floor at n=1000 tuple3 parallel=1 is noisy enough to fail A1 on its own** (M1.5, M1.6, M2.3). Four crossings of the 1.5× p99 limit by `theine_unbounded` at that one shape with no hit-path regression (M2.3 did not touch `get/2` at all and crossed at 1.51× over a 362 ns floor), each cleared by a rerun of the same tree. The procedure (rerun `--sizes 1000`, pass there clears it) is in specs/09 §Decisions M1.6 and AGENTS.md; the thresholds are unchanged. If a later hot-path task (M2.8, M4.4) keeps hitting it, a bench-only task could measure the `ets` floor twice per shape, before and after the theine subjects, and report the shape's ratios against the floor measured closest in time; that changes the harness, not the limit, and would need a specs/09 Decisions entry.

5. **A heavier rewrite of a protected key left `protected_weight` above `protected_max`** (found by M2.6's eviction property at run 158 of 3_000, resolved in M2.6). `on_write` of a known key adjusted the segment weight by the delta and moved the key to its segment's MRU, but only `on_access` demoted; a 7-weight protected key rewritten at weight 9 beside another protected key exceeded the 15-weight limit of `max_size` 20. Caffeine's `demoteFromMainProtected` runs at the end of every maintenance; here `on_write` applies the `on_access` rule after a weight increase (demote the protected LRU until it fits, or move a key heavier than `protected_max` to the probation MRU), so the specs/05 §Acceptance invariant now says "after every event" (specs/05 §Events `on_write`, §Decisions M2.6). The M2.5 property had the same exposure at 100 runs and never hit it; the eviction property keeps `max_runs: 1000` (about a second).

6. **The bounded hit path and the maintenance duty cycle both miss the A1/A2 budget** (found in M2.8; (a) resolved in M2.8b, (b) resolved in M2.8c, (c) open for M2.8d). The first full `mix bench get` with the bounded subject gave `theine` p50 at 1.64–1.98× ets and ips at 0.39–0.52× at parallel 4 (table under §Benchmark log, M2.8). Two separate causes, measured in compiled loops with `+sbt db +sbwt very_long`: (a) the spec's `record/2` costs four `:atomics` ops on a full ring (add_get, get, compare_exchange through `schedule_drain/1`, plus the remote call) at 18–25 ns per op, about 105 ns over the unbounded hit, where specs/01 §Decisions had budgeted about 65; and (b) the maintenance process runs passes back to back under read load (98% busy with one reader at 1.7 µs per `on_access` through the private ETS tables), so at full parallelism the readers share three of four schedulers. Neither is fixable inside `get/2` alone; the first wants a cheaper ring protocol (specs/03), the second a rate limit on drain-triggered passes (specs/04). The unbounded subject is unaffected once the hit path reads a single config key. M2.8b took (a) from 105 ns to about 60 ns over the unbounded hit with a two-op ring and power-of-two masks (specs/03 §Decisions M2.8b); a third of the saving came from replacing three `rem` divisions with `band`, which is worth remembering for M4.4's refresh check. M2.8c took (b) from 99% busy to 21% with the `drain_backoff` rate limit (specs/04 §Decisions M2.8c), and the bounded p99 at parallel 1 from 1.56–2.32× to 1.05–1.57×. Two things it measured are worth keeping: under four saturating readers a pass of 256 reads takes 1.6 ms of wall time (6 µs per `on_access`, against 1.7 µs with one reader), because the maintenance process shares a scheduler with a reader and its wall-time duration includes being descheduled, which M2.11's `pass_budget` measurement must expect; and `k` 7 against 3 gains about 1% of reads/s, so the knob is not the lever for what remains. (c) What remains is the hit path: at parallel 4 the bounded subject runs at 0.86–0.90× of `theine_unbounded`, which itself sits at 0.67–0.72× `ets` on the tuple3 shapes, so A2 fails there (0.57–0.62×) and passes on the binary_1kb shapes (0.71–0.72×); and at parallel 1 the bounded overhead over the unbounded hit grows with n (52, 91, 99 ns at n = 1000, 100000, 1000000) where the two-op protocol should be constant. M2.8d measured the growth and tried the layout levers; A2 is not relaxed. (c) is closed as a recorded floor (specs/09 §Decisions M2.8d): with no passes running the bounded hit is a flat 44–56 ns over the unbounded one at every n, the growth is the concurrent maintenance pass, and the ring levers measured 0 ns at one reader and at most 8–25 ns at four, below the bench's wander, so none was adopted. The reference machine turned out to be two cores with SMT (AGENTS.md), where an atomics op under a busy sibling costs about 65 ns, which is why `parallel: 4` on the tuple3 shapes cannot meet A2 with two ops however they are laid out. (d) The growth itself is the pass's memory traffic through the private policy tables and the sketch, which share the L3 with the reader and grow with n; it survives putting the maintenance process on the other core, and halving the pass rate (`drain_backoff` 7) halves it. That is a maintenance-side lever, M2.11b. (d) is closed as a recorded floor (specs/04 §Decisions M2.11b), and its premise was wrong. With `+S 2` the maintenance process was not on the other core: it ran on the pinned reader's own scheduler. So the growth is the pass's CPU time taken from that reader, and it grows with n because each drained read costs more in larger tables. M2.11b cut that cost by about a quarter (integer `order` keys, a bignum-free sketch hash, fewer struct updates). The gap went from 42–54 ns to 37–38 ns; 20 ns would need the cost halved again.

8. **A pass applies more write events than it can evict, so the table grows past the A5 bound under saturating writes** (found in M2.11; the A5 part resolved in M2.11c by eviction on arrival, specs/04 §Decisions M2.11c; the pass budget part resolved in M2.11d by capping the flush at `write_batch`, specs/04 §Decisions M2.11d). The write-count trigger runs a pass after `write_batch` (256) applied events, and that pass's step 1 flushes up to `write_batch * 4` (1024) more before step 5 evicts at most `evict_batch` (1024): under writers that keep the mailbox full every pass applies 1280 and evicts 1024, and the policy's weighted size grows by 256 per pass with nothing to stop it but the deferred `:drain` follow-ups (which also flush). Measured with `bench/results/overshoot-m211.exs` at `max_size` 10_000: the policy at 3× `max_size` after 2 s while `pending` sat at its 1028 bound; at 1_000_000 through `mix bench maintenance`, a worst sample 156 k over the bound and 128 k still over a second after the writers stopped (§Benchmark log M2.11). Even with the eviction cap raised the bound as specs/03 states it (`max_size` + `write_hwm` + in-flight inserts) cannot hold with batched eviction, because every event applied but not yet evicted is outside `pending` and inside the table, and the sampler sees the pass mid-way; it holds by construction only if an event is not consumed (its `pending` decrement) until the cache fits again, which means evicting as each `:put` is applied (Caffeine's writer runs `maintenance` inline when its buffer is full, which is the same idea). A prototype of that (one `evict/1` after each `on_write`, `pending` decremented after it) passed both A5 checks at 1_000_000 with the worst sample exactly at the bound and 10% more write throughput, and leaves the pass's step 5 a no-op except after a rebuild. It changes when evictions happen relative to a batch's reads (writes are already applied ahead of the pass's reads, so the eviction moves ahead of them too; with one access per pass, Caffeine's simulator order, nothing changes), so it is a policy task that needs `mix bench hitrate` and decisions in specs/03 (what "consumed" means), specs/04 (§The pass: eviction on arrival, the `evicted` measurement as a since-last-pass count) and specs/05 (`evict()` "called once in every pass"). Separately, the pass budget fails in the mixed run with or without the fix (p99 8.5–8.9 ms, max 12.7–21.3 ms at 1_000_000) because a saturated process always has about 1000 events to flush and each costs about 7 µs with its eviction under four workers on the two-core reference machine; the flush cap is the lever (M2.11d), since events are applied on arrival anyway and the flush exists only so that step 3 sees a current policy.

10. **The mixed-run pass p99 is within 1 ms of `pass_budget` since the sweep landed** (found in M3.1, open; not a failure). `mix bench maintenance` passes 4/4 with p99 at 3.99 and 4.17 ms against the 5 ms budget, up from 2.85–2.90 ms (§Benchmark log M3.1). A later maintenance task (M3.2, M6.2) that pushes the p99 over the budget should first split the pass by step, as M2.11d did (`bench/results/pass-steps-m211d.exs`), before it changes anything. specs/04 §Budget's lever is the cap: a lower `expire_batch` default (1024 now), re-measured. The threshold stays where it is.

11. **maintenance_test "a sketch wider than reset_chunk resets one chunk per pass" failed once** (found in M3.2, open). It failed in about 120 full-suite runs with a pattern-match failure on pinned variables, so it is one of the `Maintenance.info/1` matches on `increments` or `reset`. The output was not kept, and 100 further runs did not reproduce it. The test's events never reach M3.2's new branches: one sender, ids rising, no removals, no expiry. A likely cause is a pass the test did not request, started by a write-count trigger, a `:drain`, or a writer blocked above `write_hwm`, running the reset before the first `info/1`. Next time: run `mix test test/theine/maintenance_test.exs --repeat-until-failure 500` and keep the failing match.

12. **A fetcher could win a fresh claim after another claimant committed, and load again** (found and resolved in M4.2, specs/07 §Decisions M4.2). Step 1 claimed with `insert_new` and loaded without checking the table again. A fetcher whose `get` missed while a load ran, and whose `insert_new` ran after that claimant had committed and released, ran the loader a second time. Racing never found it: 300 rounds of 500 fetchers had no double load, because the fetcher must be descheduled within a window of a few calls. The `:claim` pause point hits it every time. M4.5's soak would probably not have caught it either. The fix is one non-counting `:ets.lookup` per claimed miss.

13. **A refresh task killed from outside leaves its `refreshing` row** (found in M4.4, resolved in M4.4b: the row names its task, and a claim that finds it dead deletes it and claims again, specs/07 §Decisions M4.4b). The task deletes its row in `after`, which a `:kill` (or the task supervisor's restart under `rest_for_one`, which kills its children while Owner and the tables live on) never runs. The stale entry is then served forever, or until it expires, and `refresh/2` returns `{:error, :refreshing}` for that key. The same hole M4.1 closed for a killed claimant. M4.5's no-leak check would not see it: its soak kills nothing.

## Open questions

1. **Resolved 2026-10-29 by a human** (specs/00, 05, 08, 09 §Decisions): the +10 margin is on `loop` 1_000 only; `theine ≥ lru` stays on every row, OLTP included, and is met by the adaptive window, now on by default (M2.13); a `theine_static` subject with `theine ≥ theine_static − 1` on every row keeps the climber honest; the human gate compares `theine` with Caffeine's `HillClimberWindowTinyLfu` (`simple`) and `theine_static` with `WindowTinyLfu`.

2. **Open (raised 2026-10-29 in M5.1): the `put` threshold of specs/09 cannot be met by the write path specs/03 prescribes.** specs/09 asks `theine` put ips ≥ 0.5 × `ets` insert ips and prices a write as "an insert, an id allocation and a message send". The isolated `mix bench get` run with the put scenario measured 0.14–0.19× at parallel 1 and 0.03–0.06× at parallel 4 on every shape. Cachex's put was 0.32–0.42× and Nebulex's 0.06–0.12× in the same run. A compiled probe (specs/09 §Decisions M5.1) puts the floor in the design, not the code. One `send/2` of the event costs 290–330 ns, even to a suspended process, against a 145–214 ns insert, so insert plus send alone is 2.4–3.5× an insert. `Theine.put/3` is 4–5× with no consumer running, and 17–21× sustained, because a writer that outruns the one maintenance process blocks above `write_hwm` (specs/03 §Delivery with backpressure, which A5's bound rests on). The threshold stands until a human changes it. Choices:
   - (a) Keep 0.5×. That needs writes that do not each send a message, for example a striped lossless write buffer over ETS or `:atomics` that the maintenance process drains, as Caffeine's write buffer is drained. This rewrites specs/03 §Write events and the A5 argument, and is several tasks, not M5.1b alone.
   - (b) Restate the check as one the design can meet and that still catches a write-path regression. **Recommended:** make put informational against `ets`, and gate it against the rivals: `theine` put ips ≥ `cachex` put ips at parallel 1. Theine was 0.41–0.53× of Cachex there in this run, and 0.10–0.15× at parallel 4, so this check fails today too. Add a task that cuts the maintenance process's cost per write event and the backpressure round trip, measured by `mix bench maintenance`'s write run.
   - (c) Restate it as a caller-cost check in bursts under `write_hwm` (`put` p50 ≤ k × insert p50). This measures what the parenthetical prices, but needs a k from a human. The probe has bursts at 5.8–8.5× with the consumer running.
